# MES-lite 功能、页面、权限与接口矩阵

状态：当前实现基线 + 已知缺口

版本：`v0.1.430`

日期：2026-08-21

## 1. 这张矩阵解决什么问题

MES-lite 采用以下顺序规划和实现功能：

```text
业务目标
  -> 原子功能
  -> 发布到页面或弹窗
  -> 权限资源与动作
  -> API 与事务校验
  -> 审计和验收用例
```

页面不是最小权限单位。一个“生产订单”页面可以同时承载查看、新建、确认、取消、登记实绩、确认实绩和冲销等原子功能；这些功能可能共用页面，但必须在服务端按动作校验权限。

本表记录的是**当前代码事实**。当前岗位组、页面动作和剩余数据范围目标见[人员权限组与页面矩阵](./人员权限组与页面矩阵.md)。

通用附件已形成独立 `modules/attachments` 垂直模块：页面、文档和物料领域统一通过公开 client 访问；六条附件 API 不再直接访问 Prisma。读取、创建、更新、归档、文件流和 AI 单据识别必须同时校验 `attachments` 动作权限、`ownerType` 对应的业务资源权限以及 `ownerId` 对象存在性；暂存附件还必须属于当前登录账号。`/uploads/*` 不提供静态直读，只能通过鉴权 API 返回文件。

认证入口由 `modules/identity-access` 统一负责：公开注册默认关闭且只产生待审核操作员，首次微信账号同样不自动提权；首个管理员只能使用一次性服务器令牌通过 `/api/auth/setup` 显式安装。登录、注册和安装入口执行持久限流，密码连续失败会锁定账号；所有写 API 在进入登录/权限判断前先执行 Origin 同源校验。

运维接口区分 `/api/health/live` 和 `/api/health/ready`：前者只表示进程可响应，后者在无登录、无写入的边界内检查 SQLite、Prisma 迁移以及数据/附件持久目录。这些路由 Docker/Coolify 监控访问，不提供业务数据或任何维护写操作。

销售订单、发货、货箱和退货的 19 条 API 已形成完整 `modules/sales` 服务端切片：路由只做资源权限、输入校验、服务调用、审计和 HTTP 映射；定价、编号、订单占用/状态、装箱完整性、批次与库存成本过账、退货待检与 PDF 生成均由领域规则及查询/命令/状态服务所有。新增 `GET /api/returns/options` 使用 `return.read` 返回当前用户可用于创建退货的发货单，不额外要求整个发货页面读取权限。货箱读取沿用 `shipment.read` 与发货库位范围；新增/归档货箱沿用 `shipmentDispatch.update`，现场照片还叠加附件动作权限。`GET /api/scannable-documents/resolve` 只在相同读取权限与数据范围内返回 BX/SH 单据导航，不因持有二维码而绕过登录或授权。

来料登记、详情、收货、拒收和整单红冲的 5 条 API 已形成完整 `modules/receiving` 服务端切片：路由只做权限、请求校验、领域服务调用、审计与 HTTP 映射；编号、明细装配、状态约束、总库存/库位/成本层过账和反向恢复由领域规则及详情/状态服务所有。`v0.1.373` 起收货逐行查询是否存在已发布的 `MATERIAL_IN` 检验标准：有标准的行进入 `QUARANTINE` 并自动建立质量任务，无标准的行仍直接进入 `AVAILABLE`。`v0.1.374` 起草稿编辑、收货/拒收和红冲分别使用 `materialIn.update`、`materialInReceive.update` 和 `materialInReverse.update`；质量任务读取与判定继续要求质量资源及库位范围。

派工列表、详情、创建、归档以及派工/开工/完工/取消的 6 条 API 已形成完整 `modules/production` 派工切片：路由只做权限、Schema、服务调用、请求级审计与 HTTP 映射；编号、工序归属、组合查询和五态流转由领域规则及查询/命令/状态服务所有。

流程转移工作区、草稿创建/编辑、确认和冲销的 4 条 API 已形成完整 `modules/production` 流程转移切片：路由只做权限、Schema、操作人、服务调用、审计和 HTTP 映射；编号、候选装配、来源库位校验、成对流水和反向库位恢复由领域规则及查询/命令/状态服务所有。

供应商与客户共用 `modules/configuration` 往来单位切片：页面复用参数化资源页，两条 API 只声明资源类型；输入契约、搜索、差异化唯一性、排序、写入、归档和 HTTP 审计适配由配置领域所有。`v0.1.360` 起维护动作分别校验 `suppliers` / `customers`；订单、来料等候选查询只在目标业务资源或对应资料资源至少一项可读时开放。

库位配置也已形成独立的 `modules/configuration` 垂直切片：API 只处理登录/权限、Schema、服务调用、审计和响应；默认库位、编码规范化、数量汇总、库存和待处理单据引用阻断、归档与恢复由纯规则及查询/命令服务所有。库位维护校验 `locations`；来料、生产、库存、发货、退货和流程转移只读候选仍可按各自业务资源读取，不能借候选接口取得库位维护权。

旧生产日报没有页面入口，生产实绩唯一入口仍是生产订单详情。`POST /api/daily-production-reports` 自 `v0.1.349` 起固定返回 `410`，禁止产生新旧日报；其余查询、修改、确认和冲销路由仅服务既有历史记录，继续校验 `stats` 权限并委托 `modules/production`。

生产订单下的 `/pick`、`/reports` 和 `/stock-in` 同样没有当前页面调用，只允许处理 `materialId=null` 的历史工单。三条 URL 继续执行原 `orders` 权限和历史兼容规则；已绑定 `Material` 的工单固定返回 `410`，新生产过账必须使用生产订单详情中的 `ProductionOrderActual` 生命周期。

库存一致性检查和 `PATCH /api/stocks` 补齐只面向有效 `Material`。Product 独占库存只由模型收敛审计报告，不再自动创建或修复。

`v0.1.353` 的 Product→Material 审计、计划和回填是容器 Terminal 内的单实例维护命令，不是 Web API 或普通页面功能。映射需要业务人员离线签字，回填前自动创建数据库+附件一致备份；不得为方便操作而暴露未鉴权管理接口。

新 Material 生产订单创建为 `DRAFT`，具有 `orders.update` 权限的人员可在详情页通过 `/api/orders/:id/confirm` 显式发布为 `RELEASED`；未发布订单不能派工或登记班后实绩。确认第一条实绩后订单进入 `IN_PROGRESS`，达到计划数量后进入 `COMPLETED`，冲销全部确认实绩后回到 `RELEASED`。历史订单状态只在读取、筛选、仪表盘和 AI 查询中归并，不批量改写。

`v0.1.354` 在生产订单详情内增加“产出批次与质量”功能。确认新生产实绩时，每项产出自动生成一个内部批次、待检库存与待检任务；当时判定使用 `quality.update`。`v0.1.357` 已将该门禁迁移为 `qualityDecision.update`，`orders.update` 仍不能代替质量判定权限。判定入口调用 `PATCH /api/quality-inspections/:id/decision`，事务同时更新检验结论、批次余额、汇总/库位库存、成本层状态、批次交易和库存流水，并保存当前登录操作人。

`v0.1.358` 新增“批次追溯”页面，仍复用 `stocks.read`，不另造权限资源。`GET /api/inventory-lots?keyword=...` 可按供应批号、内部批号、物料、供应商、客户、来料/生产/检验/发货/退货单搜索，`GET /api/inventory-lots/:id/panorama` 只读展开最多 300 个有效生产和退货关系；服务端忽略已冲销关系并重新校验权限。

`v0.1.359` 在仪表盘首屏增加服务端权限驱动的岗位任务区。生产订单发布、生产实绩草稿登记、生产实绩确认过账和生产实绩冲销分别使用 `productionOrderRelease.update`、`productionActualEntry.update/delete`、`productionActualConfirm.update` 和 `productionActualReverse.update`；任务卡只负责带 `task` 参数直达业务页，API 会再次校验同一命令资源。`v0.1.361` 起生产、质量和仓储任务数量同时受本人/工作中心生产范围和库位库存范围约束，账号审核任务仍按权限资源生成。

`v0.1.360` 将运行时资源从 30 个扩展到 48 个：流程转移、BOM 结构、客商员工、库位单位、工艺资料、业务/显示/导航/AI 设置、归档、审计和数据工具均有独立资源。`system`、`permissions` 只保留为升级兼容资源，不再作为页面注册或当前业务 API 的门禁。`GET/PUT /api/system/settings` 必须携带 `scope=business|display|ai`，服务端只返回和修改该范围字段；页面、API、AI 工具及附件所属对象统一使用细分资源。

`v0.1.361` 增加账号级数据范围：生产支持全厂、本人和指定工作中心，库存支持全部和指定库位。列表、详情、统计、任务、附件、批次追溯和状态动作在服务端复用同一范围；个人覆盖只允许保存有原因、授权人和起止时间的临时记录，到期自动失效。旧账号缺少范围记录时保持原全厂行为并标记待审批，旧个人覆盖标记为历史永久兼容。

`v0.1.367` 封闭归档工具的横向越权路径：归档列表同时要求 `archive.read` 和目标对象原业务资源 `read`，恢复同时要求两侧 `update`，永久删除同时要求两侧 `delete`；来料、生产订单、派工、发货和退货继续叠加人员数据范围。列表只返回允许类型、范围内记录和最小展示字段，前端动作由服务端返回的模型级动作能力决定。

`v0.1.369` 将运行时资源增加到 49 个。设备台账读取继续使用 `equipment.read`，只有 `equipmentEvents.update` 才能调用 `POST /api/equipment/:id/events` 执行开机、停机、故障和恢复；基础资料输入严格拒绝 `status`。事件读取 `GET /api/equipment/:id/events` 对设备只读岗位开放，状态快照和事件在同一事务保存，归档也写 `ARCHIVE` 事件。升级安装从原 `equipment` 复制新资源设置，已有新资源设置不覆盖；新安装的设备维护组使用 `equipmentEvents:RU`。

`v0.1.370` 将运行时资源增加到 50 个。设备点检页面使用 `equipmentInspections.read/create/update`，`GET/POST /api/equipment-inspections` 查询/建计划，`PATCH /api/equipment-inspections/:id` 暂停/恢复，`POST /api/equipment-inspections/:id/complete` 完成一次完整清单。查询、设备候选、执行和点检附件都叠加工作中心数据范围；异常点检联动 `FAULT` 事件时不额外授予设备事件命令权限，联动由点检领域事务产生。旧安装按 `equipmentInspections → equipmentEvents → equipment` 递归继承既有标志且不覆盖已有设置；新安装的设备维护组使用 `equipmentInspections:RCU`。快捷帮助的当前页面和完整目录分别新开 `/help?pageKey=…` 与 `/help`，仍沿用登录会话和服务端 SOP 权限过滤。

`v0.1.371` 将运行时资源增加到 51 个。设备维保页面使用 `equipmentMaintenance.read/create/update`；8 条 `/api/equipment-maintenance*` Route Handler分别提供查询、建计划、暂停/恢复、计划工单、故障维修工单、开始、完成和取消。查询、设备候选、工单命令与附件叠加工作中心范围；备件候选和领用还叠加库位范围，并在完成事务中复用库存公开过账入口。旧安装按 `equipmentMaintenance → equipmentInspections → equipmentEvents → equipment` 递归继承且不覆盖已有设置；新安装设备维护组使用 `equipmentMaintenance:RCU`，另只读物料、库存和库位。工单开始/完成产生设备事件是维保事务的一部分，不要求用户额外拥有设备事件命令权限。

`v0.1.372` 将运行时资源增加到 52 个。质量任务页面内的检验标准工作区使用 `qualityStandards.read/create/update`；5 条 `/api/quality-inspection-standards*` Route Handler 提供查询、草稿新建/修改、复制版本、发布和停用，趋势接口 `GET /api/quality-inspections/trends` 继续使用 `quality.read` 并叠加库位数据范围。生产/退货待检任务自动快照生效标准和项目，判定仍使用 `qualityDecision.update`；附件所有者 `QUALITY_INSPECTION` 同时要求附件权限、`quality` 资源和质量任务范围。旧安装按 `qualityStandards → quality` 继承既有标志且不覆盖已有设置；质量检验组只读标准，质量处置组使用 `qualityStandards:RCU`。

`v0.1.373` 增加来料质量来源和自动隔离任务；`v0.1.374` 将来料收货/拒收和红冲从 `materialIn.update` 拆为 `materialInReceive.update` 与 `materialInReverse.update`。普通仓管可收货但不可红冲，仓库主管才拥有有原因红冲；既有安装默认不把旧通用更新升级为两个高风险命令。`quality.read`、`qualityDecision.update` 和库位范围仍分别控制任务可见性与结论。待检来料红冲取消尚未完成的任务并反向恢复隔离库存；已合格且未被下游处理的批次可红冲，失败或已经发生下游业务的批次会被服务端阻断。

| 快捷搜索/高级搜索 | 继承当前页面资源 | 公共顶部工具栏 | 页面声明字段范围；API 或客户端查询不得绕过页面数据权限 |
| 页面二维码 | 继承当前页面资源 | 公共工具菜单 | 二维码只是深链接，不授予额外访问权限 |
| 弹窗全屏切换 | 继承当前页面资源 | 公共弹窗骨架 | 只改变呈现尺寸，不改变页面键、权限和数据来源 |
| 导入/导出 | 继承当前业务资源 | 页面工具栏 | 当前多映射为 `create`/`read`；敏感批量操作应继续细分和审计 |
| 归档记录 | `archive` + 原业务资源 | 工具 > 归档记录 | 读取、恢复、永久删除分别要求两侧同名动作；有数据范围的业务单据继续按人员范围过滤和断言 |

## 4. 当前权限算法

1. `ADMIN` 返回全部资源权限。
2. 非管理员没有权限组时，使用 `OPERATOR` 或 `AUDITOR` 角色默认权限。
3. 一旦人员加入权限组，只合并其所有权限组，不再叠加角色默认权限。
4. 当前有效的个人临时授权最后执行，并替换该资源的完整五项标志；过期记录不参与计算，历史永久覆盖只作升级兼容。
5. 五个通用动作是：`read`、`create`、`update`、`delete`（界面语义为归档）、`grant`。
6. 前端菜单和按钮只负责可见性；真正安全边界是 API 的 `requireResourcePermission` 及领域事务校验。
7. 当前 62 个资源按六个区段呈现；`system` 和 `permissions` 位于“升级兼容资源”，只用于为旧安装补齐普通资源，新增 `cadPreviewSettings` 从旧 `system` 安全继承，不再把新页面或 API 直接挂到宽资源；来料收货/红冲以及七个物流状态命令属于显式审批资源，不从旧通用更新自动继承。
8. 首次补齐新资源时，既有角色、既有预置组、自定义组和个人覆盖从映射的旧资源复制五项标志；已有新资源设置不会被预置值覆盖。
9. 资源动作权限通过后，生产与库存相关查询和命令继续校验 `OperatorDataScope`；管理员固定全厂，其他账号按明确范围或旧版兼容范围执行。

## 5. 已知缺口

- 生产发布、实绩登记、确认和冲销，来料收货/拒收与红冲，以及发货、签收、取消、退货收货/拒绝和流程转移确认/冲销均已拆为独立资源；销售订单确认/取消、派工状态、导入和导出等仍按各自现有资源与动作控制，后续按真实风险和岗位口径继续审计。
- 设备运行事件、设备资料、周期点检与维保工单已分权；自动设备采集、停机原因、节拍和 OEE 尚未建模。
- 质量已有跨工单任务工作区、生产/退货/来料标准版本、自动抽样、逐项结果、附件、趋势、四层动作权限和库位数据范围；SPC/过程能力、原因分类与复杂审批仍未建设。
- 本人、工作中心和库位范围已交付；部门/班组尚未独立建模，旧账号的兼容全厂范围须在生产审批中逐人收窄。
- 个人临时授权已有原因、授权人、开始与失效时间；历史永久覆盖仍须重新审批，个人例外不能作为日常岗位分配方式。
- 当前没有自动生成的 OpenAPI；本矩阵只标出主要 API 入口。

这些缺口是后续权限改造任务，不代表页面没有任何保护。改造前必须同时修改页面注册、API、AI 工具过滤、权限预置、迁移和验证脚本，不能只改菜单名称。

## 6. 新功能登记模板

新增功能时先补齐下面一行，再开始编码：

| 字段 | 要填写的内容 |
| --- | --- |
| 功能 ID | 稳定、与页面标题无关的内部标识 |
| 用户与目标 | 谁在什么场景完成什么任务 |
| 输入与输出 | 表单、附件、关联对象、生成结果 |

| 权限资源与动作 | 前端可见性和服务端校验点 |
| API/用例 | Route Handler 与领域用例入口 |
| 数据不变式 | 状态、库存、成本、单位、关联和归档约束 |
| 审计 | 是否记录原因、前后快照和操作人员 |
| 验收 | 可重复的成功、无权限、空/错状态和回退用例 |
