# MES-lite 人员权限组、页面与操作矩阵

状态：当前实现基线 + 剩余治理目标（`v0.1.367` 已交付 48 个细分资源、16 个岗位/兼容预置组、六区权限矩阵、人员数据范围、个人临时授权和归档对象二次授权）。

本文用于统一回答三个问题：人员应该加入哪些权限组、权限组可以进入哪些页面、进入页面后可以执行哪些操作。矩阵以当前页面注册表和后端权限资源为依据，但同时标出需要拆分的过粗权限资源，避免把页面可见性误当成完整授权。

## 1. 权限动作

| 代码 | 系统字段 | 含义 |
| --- | --- | --- |
| `R` | `canRead` | 查看页面、列表和详情 |
| `C` | `canCreate` | 新建记录或业务单据 |
| `U` | `canUpdate` | 修改、提交或执行状态动作 |
| `A` | `canDelete` | 归档；业务页面不直接物理删除 |
| `G` | `canGrant` | 将对应权限授予其他人员或权限组 |

`RCU` 表示同时具有查看、新建和修改权限；空白表示没有入口和操作权限。`v0.1.359` 已把生产订单发布、实绩草稿登记、实绩确认过账和实绩冲销拆为独立资源；`v0.1.360` 又将流程转移、BOM、主数据、业务设置和运维工具从宽泛资源拆开。其他高风险状态动作仍需按风险继续拆分。

## 2. 建议权限组

| 组代码 | 权限组 | 典型人员 | 边界 |
| --- | --- | --- | --- |
| `BASE` | 基础访问组 | 所有正式账号 | 只提供通用只读入口，不包含业务写入 |
| `PROD_EXEC` | 生产执行组 | 操作工 | 查看任务、报工、扫码和流程转移，不建立生产计划 |
| `PROD_LEAD` | 生产管理组 | 班组长、生产主管 | 生产订单、派工和现场异常处理 |
| `WH_EXEC` | 仓库作业组 | 仓管员 | 来料、收发、移库和库存执行 |
| `WH_LEAD` | 仓库管理组 | 仓库主管 | 在仓库作业基础上维护库位并处理归档 |
| `QUALITY` | 质量检验组 | 质检员 | 使用质量任务工作台和 `qualityDecision` 记录客观检验结果，不自动获得不合格处置或授权放行 |
| `QUALITY_DISPOSITION` | 质量处置组 | 质量工程师、处置协调人 | 使用 `qualityDisposition` 执行复检、返工和报废，不自动获得让步/解冻放行 |
| `QUALITY_RELEASE` | 质量授权放行组 | 质量负责人 | 使用 `qualityRelease` 执行让步与解冻，应限制为少量经批准人员 |
| `PROCESS` | 工艺技术组 | 工艺、BOM 工程师 | 物料、BOM、工艺、单位和作业文件维护 |
| `PLANNING` | 生产计划组 | 计划员 | 生产计划、派工计划和跨模块只读信息 |
| `EQUIP` | 设备维护组 | 设备管理员、维修员 | 设备台账与维护资料 |
| `DOC` | 文档管理组 | 文控人员 | 文档、类别、版本、附件和归档 |
| `SALES` | 销售发运组 | 销售、跟单、发运人员 | 客户、销售订单、发货和退货 |
| `PERSONNEL` | 人员管理组 | 人事、账号审核人员 | 员工档案和账号启停，不授予业务权限 |
| `PERMISSION` | 权限管理员组 | 指定安全管理员 | 权限组和人员赋权，不自动拥有系统维护能力 |
| `SYS_ADMIN` | 系统管理员组 | 系统负责人 | 全部页面和动作；控制在一至两人 |

分配规则：除 `SYS_ADMIN` 外，正式账号先加入 `BASE`，再按岗位叠加一个或多个业务组。当前数据库代码分别为 `base_access`、`production_executor`、`production_lead`、`warehouse_executor`、`warehouse_lead`、`quality_inspector`、`quality_disposition`、`quality_release`、`process_engineer`、`production_planner`、`equipment_maintenance`、`document_control`、`sales_fulfillment`、`personnel_manager`、`permission_admin` 和 `system_admin`；另保留 `basic_entry`、`business_audit` 兼容旧角色。初始化只补齐缺失设置，不覆盖管理员已经调整的权限。不要按人员姓名创建权限组，也不要使用“综合权限组”复制多个岗位权限。

## 4. 组、页面与操作矩阵

以下为当前新安装的内置预置矩阵。`SYS_ADMIN` 对全部页面拥有 `RCUAG`，不在每行重复。没有列出的组对该页面无权限。`BASE` 只提供公共只读能力，业务写入必须来自岗位组。升级安装为了保持既有行为，会从旧资源复制到新资源，不会自动把既有同名岗位组改成这里的新默认值，部署后必须复核并主动收窄。

## 5. 跨页面能力

| 能力 | 当前资源 | 当前规则与剩余目标 |
| --- | --- | --- |
| AI 协作助手 | `aiAssistant` | `BASE:R` 只允许打开助手；实际工具继续按目标业务资源二次过滤 |
| 附件 | `attachments` | 全局附件动作与所属单据权限必须同时满足；查看继承所属单据 `R`，上传继承 `C/U`，归档继承所属单据维护权限；暂存附件还按登录账号隔离，不授予脱离业务对象的附件访问 |
| 权限总入口 | `permissionUsers` / `permissionGroups` | 页面和 API 已停止依赖 `permissions`；旧资源仅用于升级兼容 |
| 个人权限覆盖 | `OperatorPermissionOverride` | 只处理例外，必须记录原因、授权人、开始时间和失效时间；到期自动失效，不作为日常分配方式；历史永久覆盖标记为待重新审批 |

## 6. 人员数据范围

权限资源回答“能做什么”，数据范围回答“能对哪些业务数据做”。两者必须同时满足，任务卡、页面列表、详情、统计、附件和写接口不得只做其中一层。

| 范围 | 模式 | 当前含义 |
| --- | --- | --- |
| 生产 | `ALL` | 全厂生产订单、派工、实绩、统计和任务 |
| 生产 | `SELF` | 仅绑定员工的派工与实绩，以及由本人派工关联的生产订单 |
| 生产 | `WORK_CENTERS` | 所选工作中心的工序、派工、订单、实绩、统计和任务 |
| 库存 | `ALL` | 全部库位及其来料、发货、退货、转移、批次、质量与库存事实 |
| 库存 | `LOCATIONS` | 所选库位相关的来料、发货、退货、转移、库存、流水、批次追溯和当前质量任务 |

管理员固定为 `ALL / ALL`。旧账号没有 `OperatorDataScope` 记录时继续兼容原全厂范围，权限页显示“继承旧版默认”，上线后必须逐人审批并保存明确范围。新注册和首次微信登录账号写入 `SELF / LOCATIONS`，其中空库位集合默认看不到库存业务数据；启用本人范围前必须绑定在职员工。

## 7. 当前实现与落地顺序

当前有效权限算法为：管理员全权；非管理员无权限组时使用角色默认权限；一旦加入权限组，只合并所有权限组，不再叠加角色默认权限；个人覆盖最后替换对应资源。这意味着给人员分配岗位组时必须同时分配 `BASE`。仪表盘按这份服务端有效权限生成生产、质量、仓储和系统任务区；任务入口不授予新权限，进入页面和提交 API 时仍会再次校验。权限页把 48 个资源分为六区，`system` 与 `permissions` 固定放在“升级兼容资源”底部。

建议实施顺序：

1. 生产部署前逐人审批并保存本人/工作中心和库位范围，清零“继承旧版默认”的非管理员账号；部门/班组范围有明确业务需求后再单独建模。
2. 逐项重新审批历史永久个人覆盖，将其改为有期限临时授权或删除；临时替岗结束可在到期前主动移除。
3. 继续拆分其他高风险状态动作；归档记录已完成原对象资源与数据范围二次校验。
4. 继续扩展矩阵覆盖校验，确保每个页面键、任务卡、API、附件和 AI 工具都能追溯到稳定权限资源及数据范围。

本文同时记录当前已交付基线与剩余目标；实际授权仍以 `lib/permissions.ts`、数据库权限组设置和 API 门禁为准。预置组不会替代企业的岗位审批，也不会自动为既有人员分组。
