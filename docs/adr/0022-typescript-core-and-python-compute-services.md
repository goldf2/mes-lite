# ADR 0022：TypeScript 业务核心与按需 Python 计算服务

## 状态

已采纳，2026-08-06。

## 背景

MES-lite 已使用 Next.js、TypeScript 和 Prisma 实现页面、API、账号权限、业务规则、生产与库存事务、审计及文档能力。系统的主要负载是数据库和网络 I/O，而不是持续的大规模数值计算。

未来可能出现 OCR、机器视觉质检、APS 排程、预测性维护、复杂数据分析和本地模型推理。这些能力可能受益于 Python 的算法与机器学习生态，但不应因此复制或重写已经形成的业务主系统。

## 决策

- TypeScript 主系统继续作为账号、权限、主数据、BOM、工单、库存、成本、审计和外部接口的唯一业务事实源。
- 生产数据库目标为 PostgreSQL；数据库迁移、可靠备份和事务一致性的优先级高于拆分语言或微服务。
- 图片、PDF、导入导出和通知等通用耗时任务优先进入任务队列，由 Node.js Worker 处理。
- 只有在存在明确算法需求、可测量收益和稳定输入输出契约时，才增加独立 Python 服务。
- Python 服务通过受控 API 或任务队列接收请求并返回结构化结果。最终业务写入、权限检查、人工确认和审计仍由 TypeScript 主系统执行。
- Python 默认不得直接写核心生产业务表。确需读取大量数据时，使用受控导出、只读副本、专用分析库或经过审批的最小只读权限。
- 每个 Python 服务必须独立版本、部署、监控和回滚，并定义超时、失败、重试、幂等、数据脱敏和结果可追溯规则。
- 不为普通 CRUD、筛选、表单、权限、报表或库存事务建立 Python 镜像实现，也不进行全量后端语言迁移。

## 引入判断

适合引入 Python 的候选能力包括：

- OCR、文档结构识别和图像内容提取；
- 机器视觉质量检测；
- 约束排程、组合优化和仿真；
- 预测性维护、异常检测和统计建模；
- 本地 AI 模型推理及训练流水线。

如果功能只是调用外部 AI API、生成普通报表或执行常规数据转换，默认仍由 TypeScript 或 Node.js Worker 实现，除非验证表明 Python 方案在能力、维护或成本上有明确优势。

## 结果

- 当前团队可以继续复用前后端类型、校验和业务模块，不承担整体重写的回归风险。
- Python 能力可以按垂直切片逐项接入，不会形成第二套权限、库存和生产规则。
- 混合架构会增加服务通信、监控和部署成本，因此只有达到引入门槛的功能才能拆分。
- Python 服务发生故障时，主业务系统应保持可用；相关功能显示任务失败、可重试或降级，不得阻塞基础生产操作。
