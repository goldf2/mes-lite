# ADR-0043：生产 Schema 漂移必须通过非覆盖候选收敛

状态：已接受
日期：2026-08-15

## 背景

生产 SQLite 曾应用后来从主线撤回的迁移。即使 `prisma migrate deploy` 能将当前迁移记录补齐，物理表、索引和旧列仍可能留在数据库中。直接在生产原库执行 `prisma migrate diff` 生成的重建 SQL，会将结构判断、历史数据去向和不可逆修改捆绑在一次操作中。

## 决策

1. 目标 Schema 的权威基线是指定 Git 提交中全部 `prisma/migrations/` 在空库上的执行结果，而不是单独的 `schema.prisma`。
2. 先对稳定复制品做只读审计，源数据库不由 SQLite 打开，且报告不可覆盖。
3. 如存在带数据的退役结构，先归档建表 SQL 与数据，再由业务负责人批准处置；开发人员不得独自判定删除。
4. 收敛 SQL 只在新建候选上执行。候选必须通过 SQLite 完整性、外键、后置零漂移审计和应用级恢复演练。
5. 生产切换仍需新的数据库+附件一致备份、RPO/RTO 门禁、业务签字、真实 Coolify 挂载切换与可回切旧挂载。

## 后果

- 任何收敛失败只需丢弃候选，不需对生产原库执行反向 SQL。
- 迁移记录正常和物理 Schema 一致被分开验证，避免将 `schema up to date` 误当作零漂移。
- 会额外生成审计、归档、候选和应用演练四类证据，但这些成本换取了可审批、可回滚和不覆盖的生产边界。
