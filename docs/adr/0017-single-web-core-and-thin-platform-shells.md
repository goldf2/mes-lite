# ADR 0017：MES-lite 多平台采用单一 Web 核心与平台薄壳

## 状态

已采纳，2026-08-05。

## 背景

MES-lite 当前由 Next.js 提供响应式 Web 页面和服务端 API，并通过 Coolify 部署。系统未来可能需要 Windows、macOS、Android 和 iOS 客户端，以便使用扫码、拍照、打印、文件和自动更新等原生能力。

如果为每个平台复制一套业务页面和领域逻辑，来料、生产、库存、发货、退货和 BOM 的变更将需要重复实现与验证，版本容易分叉，也会在 Web 核心流程尚未稳定时显著增加发布成本。

## 决策

- 保留一套 Next.js 前端、API、权限、领域规则和数据库模型，作为所有平台的唯一业务事实源。
- Web 版继续由 Coolify 部署；平台客户端默认连接同一生产服务，不内置生产数据库或完整后端。
- 桌面客户端优先采用 Tauri，移动客户端优先采用 Capacitor。平台工程只包含启动壳、环境配置、签名、更新和原生桥接代码。
- 扫码、拍照、打印、文件、通知、串口等原生能力通过平台适配接口注入共享前端；业务组件不直接绑定 Tauri、Capacitor 或特定操作系统 API。
- 多平台发布按 Web、Tauri 内部测试、Android 内部测试、iOS/商店/离线能力的顺序推进。Web 核心业务闭环稳定前，不建立多条长期并行的业务开发线。
- 所有发布形态共享语义版本号；各平台构建号独立递增，签名和商店密钥由部署环境管理。

## 结果

- Web 功能更新可以直接进入大部分桌面端和移动端页面，平台工作集中在构建、分发和原生能力适配。
- 平台差异必须通过明确适配层处理，不能在共享业务组件中散布操作系统判断。
- App 不能天然获得离线能力；离线数据、冲突解决和补传机制需要独立建模和验收。
- 平台发布仍会增加签名、商店、安装包、升级和设备测试成本，但不会形成多套业务代码的长期维护负担。
