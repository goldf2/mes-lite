# ADR-0029：已发布 BOM 版本不可变

- 状态：已接受
- 日期：2026-08-12

## 背景

BOM 是生产关系和生产订单的计算依据。旧实现允许直接覆盖同一 BOM 的投入、产出和比例，虽然生产订单保存了快照，但主数据界面无法区分未完成草稿、正式生效版本和退出使用的历史版本，也容易把“修改正式版本”误认为普通资料编辑。

## 决策

1. BOM 使用 `DRAFT -> RELEASED -> OBSOLETE` 单向生命周期。
2. 只有 `DRAFT` 可编辑；`RELEASED` 和 `OBSOLETE` 永久只读，调整正式关系必须从旧版本复制出新草稿。
3. 同一内部产品的 `productId + version` 保持数据库唯一，版本号不允许重复复用。
4. 发布时将当前草稿设为同一产品、同一用途的默认版本；旧已发布版本继续保留，但不再默认。
5. 作废只改变后续可选性，不删除 BOM、明细或历史订单引用；若作废默认版本，系统选择最近的其他已发布版本作为默认。
6. 生产订单、包装库存穿透和默认成本读取只使用 `RELEASED` BOM。生产订单继续保存 `bomId`、名称、版本和完整快照，后续 BOM 状态变化不回算历史订单。
7. 已有启用 BOM 在迁移时转为 `RELEASED`，已有停用 BOM 转为 `OBSOLETE`，避免升级后中断现有生产候选。
8. 发布、复制版本和作废均通过领域服务并写入操作审计；不建立重复的 BOM 状态表。
9. SQLite 运行库使用触发器阻止已发布/已作废 BOM 主体、投入和产出被直接改写，并阻止状态回退为草稿；迁移 PostgreSQL 时必须用等价触发器或存储过程保留这条数据库不变式。

## 后果

- BOM 从普通可覆盖资料变为受控生产标准。
- 新建 BOM 必须经历“保存草稿、发布”两个明确动作后才能用于生产。
- 版本派生保留 `basedOnBomId` 和可选变更原因，未来可在此基础上扩展审批，而无需改变生产订单快照规则。
- `isActive / isDefault` 暂时作为兼容投影保留；正式选择以 `status = RELEASED` 为准。
- 锯切成本、数据维护等旁路不得修改正式版本：需追加内容时自动派生草稿，一致性工具对正式版本只告警。
