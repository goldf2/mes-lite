# MES-lite 备份、恢复与灾备演练

状态：当前单实例 SQLite 运维基线

事实基线：`v0.1.375` / 2026-08-14（最近一次生产候选应用级恢复证据来自 v0.1.366；v0.1.373 已完成本地合成候选演练，v0.1.374-v0.1.375 未修改数据库或恢复机制）

生产现状：Coolify 已持久挂载 `/app/backups`，已启用迁移前一致备份和每日定时备份；生产恢复候选已完成非覆盖技术恢复和本机隔离应用启动、readiness、管理员登录、业务与附件抽查。异地 S3/另一主机和真实 Coolify 挂载切换尚未配置或执行。

## 1. 保护对象和目标

MES-lite 的生产数据由两部分组成，两者必须作为同一个恢复单元：

- `/app/data/mes_lite.db`：SQLite 业务数据库。
- `/app/public/uploads`：附件原文件和派生预览。

当前商业交付基线是：

| 项目 | 基线 |
| --- | --- |
| 备份频率 | 每日至少 1 次，每次数据库迁移前自动再备份 1 次 |
| 本机保留 | 最多 30 份且最长 14 天，先到条件生效 |
| 异地副本 | 每日将成功验证的归档与 `.sha256` 同步到另一台主机或对象存储 |
| RPO 目标 | 不超过 24 小时；关键上线以迁移前备份缩短窗口 |
| RTO 目标 | 60 分钟内生成恢复候选、切换挂载并完成冒烟验证 |
| 演练频率 | 至少每季度 1 次，每次重大迁移前再演练 |

RPO/RTO 是当前交付目标，只有记录真实演练时间后才能作为已验收承诺。

## 2. 备份包如何保证可恢复

`scripts/runtime-backup.mjs create` 执行以下闭环：

1. 使用 SQLite `VACUUM INTO` 生成一个一致数据库快照，不直接拷贝可能处于 WAL 写入中的数据库文件。
2. 拷贝附件目录，禁止符号链接和超出持久化根目录的附件记录。
3. 读取快照中每条 `DocumentAttachment.storagePath`，确认对应原文件已进入备份；遇到并发上传/删除导致不一致时最多重试 3 次。
4. 对 SQLite 快照执行 `PRAGMA quick_check`，生成包含版本、时间、附件数和逐文件 SHA-256 的 `manifest.json`。
5. 生成 `mes-lite-backup-*.tar.gz` 及同名 `.sha256`，再从归档中解压并重做校验。只有验证成功后才执行保留策略。

此策略允许在单实例运行期间备份；恢复切换仍必须停止应用，不允许在 Next.js/Prisma 仍持有数据库连接时覆盖 SQLite 或 uploads。

## 3. Coolify 日常备份

Coolify 必须挂载第三个持久化目录。当前生产应用实际使用：

```text
/data/coolify/applications/yjad2gnk1ycpeletd0aqlq4g/backups -> /app/backups
```

在 Coolify Scheduled Tasks 中建立每日任务。当前生产容器已实测时区为 UTC，因此北京时间每天 02:00 使用 `0 18 * * *`；其他服务器必须先核验容器时区，不能照抄时刻：

```bash
node /app/scripts/runtime-backup.mjs create
```

当前生产任务：`MES-lite 每日一致备份`，超时 1800 秒。2026-08-13 首次手动执行成功，归档为 `mes-lite-backup-2026-08-13T10-54-48-733Z-5682619c.tar.gz`，SHA-256 为 `6fcf83745b921b4f03e4066cf4be8d663d637cb0e900f713fb7dbf293cb56fc4`；数据库 `quick_check=ok`，90 条附件记录对应 253 个清单文件。

同日固定版本重部署已验证迁移前自动备份：新容器启动日志在 `prisma migrate deploy` 前生成 `mes-lite-backup-2026-08-13T11-33-44-021Z-5330c3ab.tar.gz`，SHA-256 为 `cbcfe027ee518032247806768c2c35c811434e377a8020cabb5f6ab3be37999b`；随后确认 76 个迁移无待处理并健康启动。

可随时手动验证指定备份：

```bash
node /app/scripts/runtime-backup.mjs verify \
  --archive /app/backups/mes-lite-backup-<timestamp>.tar.gz
```

迁移前自动备份由 `MES_LITE_PRE_MIGRATION_BACKUP_ENABLED=true` 控制。为避免未配置持久化备份挂载的旧环境在升级时写满容器层，镜像内建默认为 `false`；Compose 和 `.env.coolify.example` 在配置 `/app/backups` 挂载后显式开启。旧数据库非空时，容器会在清理兼容文件和 `prisma migrate deploy` 之前创建并验证备份；备份失败则中止启动，不带病迁移。全新空库会直接进入迁移。

## 4. 异地副本

本机备份不能防止主机磁盘、账号或机房故障。每日定时任务成功后，由主机级 `rsync`/`rclone` 或云存储备份任务同步以下两个文件：

```text
mes-lite-backup-<timestamp>.tar.gz
mes-lite-backup-<timestamp>.tar.gz.sha256
```

异地副本应使用独立账号、最小写入权限和不同故障域。仓库不提供云密钥示例，任何凭据都只能保存在 Coolify 或主机密钥管理中。

截至 2026-08-13，Coolify 的 S3 Storages 页面显示 `No storage found`。因此异地副本是明确的未验收项；提供 S3 兼容端点、Bucket、Access Key 和 Secret Key 后，必须完成“上传 → 在另一环境下载 → SHA-256 校验 → 非覆盖恢复候选”再关闭该项。

## 5. 非覆盖恢复演练

先在运行容器中将备份解压到一个**不存在的新目录**：

```bash
node /app/scripts/runtime-backup.mjs stage-restore \
  --archive /app/backups/mes-lite-backup-<timestamp>.tar.gz \
  --target /app/backups/restore-candidate-<timestamp>
```

### 5.1 生成不可覆盖的演练证据

`v0.1.352` 起可以把归档验证、候选恢复、RPO/RTO 计算和 Markdown 记录合并为一个命令：

```bash
npm run storage:drill -- \
  --archive /app/backups/mes-lite-backup-<timestamp>.tar.gz \
  --target /app/backups/restore-candidate-<timestamp> \
  --report /app/backups/drill-reports/<timestamp>.md \
  --environment coolify-staging \
  --operator "值班人员姓名" \
  --rpo-hours 24 \
  --rto-minutes 60
```

命令要求候选目录和报告文件都不存在，拒绝覆盖既有记录。它会重新验证侧车 SHA-256、归档条目、逐文件清单、SQLite `quick_check` 和附件引用，随后记录备份创建时间、候选就绪时间、RPO、RTO 与阈值结论。任一 RPO/RTO 目标未达到时仍生成报告，但进程以非零状态退出，便于调度和 CI 告警。

[2026-08-12 本机隔离演练记录](./drills/2026-08-12-local-isolated-v0.1.352.md)已验证 4 条附件引用和 21 个归档文件，候选 RPO 为 255.695 秒、候选 RTO 为 0.195 秒。该机器没有 Docker，因此记录明确保留应用实例启动、readiness、登录和业务抽查为未执行；这份证据只证明恢复候选技术闭环，不代表生产环境恢复验收。

[2026-08-13 Coolify 生产恢复候选记录](./drills/2026-08-13-coolify-production-candidate-v0.1.361.md)在生产容器内使用已验证归档生成新候选目录，记录 RPO 197.472 秒、候选 RTO 11.460 秒，均达到 24 小时/60 分钟目标。在线生产未被覆盖，候选新实例的管理员登录和业务抽查仍未执行。

[2026-08-13 生产候选应用级隔离演练记录](./drills/2026-08-13-local-production-candidate-application-v0.1.366.md)继续使用该生产候选的本地只读副本，复制 252 个附件文件并逐一复核 SHA-256，启动 v0.1.366 生产构建，完成 readiness、隔离临时管理员登录、45 个物料/62 条库存/1 张生产单的只读 API 抽查，以及 83 个有效附件中的原文件 API 哈希抽查。完整应用 RTO 为 1.582 秒；源候选数据库 SHA-256 未变化，临时管理员已清理。该证据关闭“候选新实例应用抽查”项，但不代表真实 Coolify 挂载切换或异地取回通过。

### 5.2 新实例应用验收

命令会再次检查归档 SHA-256、逐文件清单、SQLite `quick_check` 和附件引用，然后生成：

```text
restore-candidate-<timestamp>/
  data/mes_lite.db
  uploads/
  manifest.json
```

脚本拒绝已存在的 `--target`，不会修改 `/app/data` 或 `/app/public/uploads`。演练应在隔离的测试容器中将 candidate 的 `data` 和 `uploads` 挂载到标准容器路径，完成：

1. `/api/health/ready` 返回 200。
2. 管理员可登录。
3. 随机抽查物料、库存、生产单和附件原文件。
4. 记录备份创建时间、恢复开始/完成时间、实际 RPO/RTO、操作人和异常。

`v0.1.366` 起可用同一生产构建在本机或独立服务器执行上述应用验收：

```bash
npm run storage:drill:application -- \
  --database /path/to/recovery-candidate/data/mes_lite.db \
  --uploads /path/to/recovery-candidate/uploads \
  --target /path/to/nonexistent/application-candidate \
  --report /path/to/nonexistent/application-report.md \
  --environment isolated-recovery \
  --operator "值班人员姓名" \
  --source-created-at 2026-08-13T03:55:00.552Z \
  --rpo-hours 24 \
  --rto-minutes 60
```

该命令要求先执行 `npm run build`。它复制源候选而不覆盖，校验数据库和全部附件 SHA-256，向复制库部署当前迁移，创建随机临时管理员后启动 `next start`，验证 `/api/health/ready`、登录、物料/库存/生产订单只读接口及附件原文件哈希，最后停止应用并清理临时管理员。报告只记录数量、哈希和状态，不记录业务明细、附件名称、临时账号或密码。

历史附件记录可能保存旧容器 `/app/public/uploads` 绝对路径。v0.1.366 会在记录严格位于该根目录时，将其相对部分安全映射到当前 `MES_LITE_UPLOAD_DIR`；其他外部路径和 `..` 越界仍拒绝。若历史实例使用其他根目录，只能在隔离演练中显式配置 `MES_LITE_LEGACY_UPLOAD_DIR`，核对后再交付，不得放宽为任意绝对路径。

## 6. 生产故障切换和回滚

Product→Material 人工回填在维护窗口前先运行只读 `preflight`，通过与失败报告都会记录映射和数据库前后 SHA-256；只有预检通过后，`apply` 才会强制调用同一一致备份机制，并把精确 `archivePath` 和 SHA-256 写入迁移报告。该类回滚必须使用报告绑定的归档，具体见[Product 到 Material 映射与回填](./Product到Material映射与回填.md)。

真实恢复时：

1. 在 Coolify 停止 MES-lite 容器，确认没有另一实例连接原 SQLite。
2. 保留当前 `/opt/mes-lite/data` 和 `/opt/mes-lite/uploads` 为带时间戳的回滚目录，不直接删除。
3. 将已验证 candidate 中的 `data` 和 `uploads` 切换为 Coolify 的两个业务挂载。
4. 启动单个实例，先验证 readiness，再完成上述业务冒烟。
5. 验收失败时停止容器，将挂载切回保留的原目录；不在运行状态下来回覆盖文件。

`v0.1.347-v0.1.352` 只增加备份、就绪和演练机制，不改写业务 Schema。`v0.1.353` 增加可空 Material 投影，`v0.1.368` 只增加只读预检；未执行回填时可回退应用代码并保留新列，已执行回填时必须使用该次报告绑定的备份恢复数据。任何回滚都必须保留已生成的备份和未跟踪的生产数据目录。

## 7. 就绪检查和告警

- `/api/health` 和 `/api/health/live`：只证明 Node.js 进程可响应。
- `/api/health/ready`：检查 SQLite 查询、镜像内迁移是否全部应用且无失败、数据目录和附件目录读写性。任一硬检查失败返回 503。
- 备份新鲜度是 readiness 中的 `warn`，默认超过 26 小时告警但不重启容器，避免“备份调度故障”被误当成“业务进程故障”导致重启循环。
- Docker `HEALTHCHECK` 和 Coolify 都使用 `/api/health/ready`。监控系统应另外解析 `backupFreshness` 告警并通知运维人员。
- 当前 Coolify 邮件通知已启用，并已勾选部署失败、备份失败、定时任务失败、容器状态变化和服务器磁盘告警。通知通道仍应按季度发送测试邮件，避免“已勾选但实际无法送达”。
