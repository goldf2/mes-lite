# 生产产出批次质检与库存状态

适用版本：`v0.1.354`

状态：当前操作与维护基线

> `v0.1.355` 已把来料、生产投入和产出接入内部批次谱系，`v0.1.356` 又把发货和客户退货接入同一质量状态服务。本页保留 v0.1.354 的生产质量操作基线；客户退货质检见[发货退货批次追溯与质检操作](./发货退货批次追溯与质检操作.md)。

## 1. 能做什么

本版本把新生产实绩的产出接入以下闭环：

```text
确认生产实绩
  → 每项产出生成内部批次
  → 数量进入待检库存
  → 自动生成待检任务
  → 整批合格放行到可用库存，或整批不合格冻结
  → 批次交易、库存流水和审计可回放
```

在适用的 v0.1.354 基线中，这还不是完整追溯系统。v0.1.355 补齐来料与生产投入，v0.1.356 补齐发货与客户退货的批次级回流；部分放行、复检、让步、返工、报废或解冻仍未实现。

## 2. 岗位与权限

| 任务 | 权限 | 默认角色 |
| --- | --- | --- |
| 查看/登记生产实绩 | `orders.read/create/update` | 依现有权限组 |
| 合格放行或不合格冻结 | `quality.update` | 审核员、管理员；普通操作员默认没有 |
| 查看库存和流水 | `stocks.read` | 依现有权限组 |

前端按钮不可见不代表安全；`PATCH /api/quality-inspections/:id/decision` 会再次校验登录会话与 `quality.update`。

## 3. 车间操作

### 3.1 产生待检批次

1. 进入“生产 → 生产订单”，打开已发布或生产中的订单。
2. 在“班后生产实绩”登记实际投入、产出、员工和库位，先保存草稿。
3. 核对数量和库位后确认实绩。
4. 在实绩产出下查看内部批次号、待检状态数量和检验单号。

确认后，产出已计入总库存，但属于待检状态，不能用于领料、发货或普通库存调整。

### 3.2 整批合格放行

1. 在待检批次卡片点击“合格放行”。
2. 录入抽检数量、合格数量、不合格数量和结论说明。合格判定要求不合格样本为零，合格数与不合格数之和等于抽检数。
3. 核对批次号和待检数量，点击“确认整批放行”。
4. 卡片显示“已放行”，库存页的可用数量增加、待检数量减少；库存流水出现 `QUALITY_RELEASE`。

### 3.3 整批不合格冻结

1. 在待检批次卡片点击“不合格冻结”。
2. 录入抽检、合格、不合格数量，并在说明中写明不合格现象和冻结原因。
3. 点击“确认整批冻结”。
4. 卡片显示“冻结”，库存页的冻结数量增加、待检数量减少；库存流水出现 `QUALITY_HOLD`。

当前没有解冻或处置入口。冻结后不要通过数据库或普通库存调整绕过状态；需要纠错时由管理员先保全备份和审计证据，再制定前滚修复方案。

## 4. 对账规则

每个受影响物料都应满足：

```text
总库存 = 可用库存 + 待检库存 + 冻结库存
总库位库存 = 汇总库存
批次状态余额 = 对应批次成本层剩余量
质量状态转换前后：总数量、核算数量、总成本不变
```

库存流水中的质量状态转换数量变化为 0，这是刻意设计：它记录状态从 `QUARANTINE` 到 `AVAILABLE/HOLD`，不是新的收发货。

## 5. 部署与迁移

1. 生产维护窗口先执行数据库与附件一致备份，并验证清单与 SHA-256。
2. 保持单实例迁移，执行 `npm run db:deploy`；迁移 `20260813090000_add_production_quality_lots` 只增加表、列和索引。
3. 启动新版本后检查 `/api/health/ready`，再用受控测试工单验证一条待检和一条判定。
4. 核对库存汇总、库位余额、批次余额、成本层、库存流水和审计操作人。
5. 本地测试结论不能代替真实 Coolify 数据和持久卷验收。

## 6. 回滚边界

- 尚未产生 v0.1.354 新批次时，可回退应用代码并保留新增空表/列。
- 已产生批次、待检或冻结数据后，不得删除新增表或直接回退旧应用；旧版本无法正确隔离这些库存。应保留 Schema、停止相关写入并前滚修复。
- 任何恢复都写入新候选路径，完成 `PRAGMA quick_check`、迁移状态和附件清单验证后再切换挂载；不得覆盖唯一生产副本。
