## 根因判断

生产应用 `yjad2gnk1ycpeletd0aqlq4g` 与演示应用 `rvus7tl6zbz5gizamg8bzedo` 都连接 `goldf2/mes-lite` 的 `main` 分支，并且 Auto Deploy 同时开启。一次 Git 推送因此在同一台 4 vCPU、约 7.1 GiB 内存且无 Swap 的服务器上并发执行两次完整 Next.js Docker 构建。

部署数据库和两条构建日志直接证明两个构建同时进入最耗资源的 `next build` 阶段；主机未安装可回放的进程级历史采样，因此无法给出故障分钟内每个 PID 的精确 CPU 百分比。结合用户看到的 CPU 满载、Coolify 健康检查随后超时和两个构建均停在同一步骤，双构建是置信度最高的直接触发器。

另有遗留 `web-terminal-ws.service` 指向已删除的 `/opt/web2py-private`，每 5 秒失败重启一次。上一个启动周期重启计数超过 108,560，持续制造 systemd/journal 写入；它不是 CPU 满载的唯一直接原因，但在构建饱和时放大了 systemd、journald 和 Docker 的响应问题。

## 恢复与回滚

关闭演示自动部署属于配置变更，回滚方式是在确认主机无构建任务后重新开启；重新开启前必须具备串行部署或独立构建资源。失效 WebSocket 服务如需恢复，先还原完整 `/opt/web2py-private` 程序、数据库和密钥，再把归档 unit 恢复到 `/etc/systemd/system/` 并执行 `daemon-reload`；不得只恢复 unit 重新制造重启风暴。

v0.1.387 只修复 CI 历史审计基线拉取并更新运维证据，没有运行时和数据库变更。其代码回滚到 v0.1.386 不会解决双构建问题；部署门禁必须在 Coolify 配置层完成。
